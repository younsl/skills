### Upstream contribution

An issue, fix, or feature for an open source project you do not own.

1. Read CONTRIBUTING, the issue and PR templates, the commit rules (sign-off, signing), and recent merged PRs for scope and tone (**principle-house-rules**).
2. Open or find an issue first, with a reproduction on a released version. Wait for direction on design questions before writing a large change.
3. Keep each PR to one reviewable change. Split a large design into sequenced PRs, and credit the prior work you build on (**principle-reviewable-units**).
4. Run the project's own test and lint targets in its supported environment, a Linux container when the workstation lacks what the tests need (**principle-proof-of-done**).
5. Write the PR body from the repo template in plain English: the problem, the change, and test evidence in a collapsed block, with permalinks for claims about the code. Nothing internal appears in code, commits, body, or images (**principle-air-gap**).
6. Answer review comments in one or two sentences: thanks and the single point.
7. Some forums accept posts only through their web form and close API-created ones. Prepare the text and hand it to the operator for those.

**Reply:** the issue and PR links, the checks run with results, and what the maintainers asked for next.
